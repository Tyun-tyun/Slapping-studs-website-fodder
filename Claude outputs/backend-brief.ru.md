# The Slapping Studs — техническое задание на бэкенд

**Репозиторий:** `slapping-studs` · чистые HTML/CSS/JS, без сборки, без зависимостей
**Статус:** фронтенд готов полностью, 17 страниц, сервера нет вообще
**Ваша задача:** дать сайту настоящий бэкенд

Всё, что описано в этой презентации, опирается на уже существующий код.
Ссылки на файлы и строки даны по текущей ветке `master`.

Читать по порядку. Одна страница = одна задача.

## 2 · Задача одним предложением

> Заменить `localStorage` на базу данных, заменить проверки прав на стороне
> браузера на серверные, и заставить обе формы реально что-то отправлять.

Три конкретные замены:

1. `Studs.load()` / `Studs.save()` → HTTP-запросы (`js/core.js:55-71`)
2. `Studs.perms` + `S.GATED` → проверка на сервере (`js/auth.js:36`, `js/routes.js:53`)
3. Обработчики `bindForms()` с `preventDefault()` → реальные POST-запросы (`js/app.js`, в конце файла)

Всё остальное в этой презентации — детали к этим трём пунктам.

## 3 · Обязательные ограничения

- **Никакой сборки.** Сайт открывают напрямую с диска не реже, чем через сервер.
  Не вводите бандлер, фреймворк или JSX. Только простой JS в духе ES5 —
  придерживайтесь существующего стиля.
- **Относительные URL.** `js/routes.js` намеренно использует `index.html`, а не `/`.
  Если переходите на чистые URL — меняйте **только** `S.PAGES` (`routes.js:27`).
- **Поле `id` — это контракт.** У каждой записи есть уникальный строковый `id`
  (`n1`, `pl01`, `sd07`). Рендереры, слоты изображений и параметры запроса
  завязаны именно на него. При миграции сохраняйте существующие id.
- **`js/data.js` остаётся** как сид / запасной вариант. Если API недоступен,
  сайт всё равно должен отрисовать сохранённый контент, а не пустую страницу.
- **Экранирование на выводе.** Функция `Studs.esc()` уже есть, единственное
  неэкранированное поле — `content.copy` (HTML, написанный админом). Оно должно
  оставаться единственным исключением.

## 4 · Рекомендации по стеку

Небольшой сайт клуба, ~60 участников, низкая посещаемость, один член правления
в роли администратора.

- **Среда выполнения:** Node 20 + Fastify/Express, либо PHP 8, если хостинг shared.
- **БД:** PostgreSQL. SQLite вполне оправдан при таком масштабе — если выбираете
  его, сразу это озвучьте.
- **Файлы:** локальный диск + nginx, либо S3-совместимое объектное хранилище.
  **Не** база данных.
- **Сессии:** серверные, cookie с флагами `HttpOnly` `Secure` `SameSite=Lax`.
  Никакого JWT в `localStorage`.
- **Хостинг:** любой, с TLS, слотом под cron для бэкапов и SMTP.

Итоговый результат — один разворачиваемый сервис плюс корень со статикой.

## 7 · Порядок имеет значение

Несколько рендереров зависят от **порядка элементов в массиве**, а не от
столбца сортировки:

- `renderStandings()` выводит по одной карточке на дивизион **в том порядке,
  в котором дивизионы впервые встречаются** в массиве (`js/views.js:258`).
  Правление меняет порядок таблиц, переставляя строки местами.
- `stats` рендерится слева направо в порядке хранения.
- `news` и `events` рендерятся в порядке хранения.
- `saveDrawer()` делает `unshift()` — новая запись попадает **в начало**
  (`js/admin.js`).

**Добавьте в каждую таблицу столбец `sort_order INTEGER`** и возвращайте
строки, отсортированные по нему. Не полагайтесь на порядок по умолчанию из БД.

## 8 · Медиа — самое крупное изменение

Сейчас: изображения хранятся как **base64 data URL прямо внутри JSON с
контентом**, уменьшенные в браузере через canvas до максимум 1200–1600 px
с качеством JPEG 0.78 (`Studs.readImageFile`, `js/core.js:99`). Именно
поэтому существует лимит хранилища в 5 МБ и всплывающее сообщение
«Storage full».

Требуется:

- `POST /api/images` — multipart, принимает **оригинальный** файл.
- На сервере: проверка реального MIME-типа (по магическим байтам, а не по
  заголовку), лимит ~15 МБ, удаление EXIF, генерация ≥2 размеров
  (миниатюра ~600 px, полный размер ~1600 px), перекодирование в WebP
  с фолбэком в JPEG.
- В записи контента хранить **URL**, а не сами байты.
- Ключи слотов остаются точно такими же: `hero`, `news:<id>`, `player:<id>`,
  `album:<id>`, `timeline:<id>`, `chapter:<id>:<n>`, `gear:<id>`.

## 10 · Авторизация — что нужно построить

- Настоящая таблица пользователей: `id`, `email`, `password_hash` (argon2id
  или bcrypt с cost ≥12), `role`, `name`, `sub` (например,
  `"Studs 2 · #14"`), `created_at`, `last_login`.
- **Удалить три демо-аккаунта вместе с напечатанными паролями**
  (`js/auth.js:21`) и карточки с учётными данными на `sign-in.html`
  (`renderSignin`, `js/views.js:951`) до публикации.
- Вход в систему: ограничение по частоте попыток (например, 5 попыток /
  15 минут / IP+email), общее сообщение об ошибке без деталей, сессионная
  cookie при успехе.
- Никакой публичной самостоятельной регистрации. Аккаунты создаёт правление;
  `signups` — это очередь заявок, а не регистрация.
- Сброс пароля — по одноразовому токену, присланному на e-mail, срок
  действия 1 час.

## 11 · API — чтение контента

```
GET /api/content            → весь стор целиком, один объект
GET /api/content/:collection
```

`GET /api/content` должен возвращать данные в том же формате, что экспортирует
`js/data.js`, чтобы `Studs.load()` превратился просто в `fetch`, а всё
остальное ниже по цепочке осталось без изменений.

**Ответ должен быть уже отфильтрован по роли вызывающего.** Не отправляйте
черновики или альбомы тренеров гостю, скрывая их через CSS.

- `Cache-Control` на публичном чтении; сбрасывать кэш при записи.
- ETag / `304` того стоят — этот payload представляет собой весь сайт.
- Неаутентифицированные вызовы получают публичное подмножество данных.
  Никакого 401 на публичном чтении.

## 12 · API — запись контента

```
POST   /api/content/:collection        → создание (id присваивает сервер)
PATCH  /api/content/:collection/:id    → обновление
DELETE /api/content/:collection/:id    → мягкое удаление
POST   /api/content/:collection/reorder
```

- Валидируйте по `S.schema` — отклоняйте неизвестные поля, проверяйте каждый
  `select:a,b,c` как enum.
- **Мягкое удаление.** `js/admin.js` `delRecord()` показывает тост с отменой
  (Undo) без диалога подтверждения. Храните 30 дней, затем удаляйте окончательно.
- «Последняя запись побеждает» приемлемо при таком масштабе, но возвращайте
  обновлённую запись, чтобы клиент перерисовывался, опираясь на данные с сервера.
- Журнал аудита: `who`, `what`, `when`, `before`, `after`. Один член правления
  в год будет наследовать эту консоль — она ему понадобится.

## 13 · API — инлайн-правки текста

`content.copy` — это плоская карта: `{ "<ключ data-ed>": "<HTML-строка>" }`.
Записывается по событию `blur` у элемента с `contenteditable`
(`js/admin.js`, `bindInlineEditing`). Удаление правки восстанавливает
исходный текст, «зашитый» в HTML.

```
PUT    /api/copy/:key     тело: { html }
DELETE /api/copy/:key     → откат к исходному варианту
```

**Это единственное поле, которое хранит HTML.** Санитизируйте на сервере
через белый список тегов (`b i em strong a br p ul ol li`, атрибут `href`
у `a` ограничен схемами `http/https/mailto`). Доступ только для админа,
но админский аккаунт можно украсть.

## 14 · API — две публичные формы

**Вступление в клуб** (`join.html`, `#joinformel`) — сейчас записывается
прямо в `content.signups` в браузере (`js/app.js`, `bindForms`).

```
POST /api/signups
{ name, email, study, experience, session, note }
→ создаёт запись в signups со статусом "new"
```

**Контакты** (`contact.html`, `#contactform`) — сейчас вообще ничего не
делает, только показывает тост об этом.

```
POST /api/contact
{ name, email, subject, message }
```

Обе формы: honeypot-поле + проверка по времени заполнения + серверный
rate limit. Без CAPTCHA, пока реально не начнётся спам.

Проверки в браузере — это просто удобство. Продублируйте каждую из них на

## 18 · Роутинг и 404

Сейчас `js/routes.js` обрабатывает неправильные URL **в браузере**, потому
что сервера нет: `S.BUILT` перечисляет документы на диске, `isDeadLink()`
проверяет по этому списку, один обработчик в `app.js` перенаправляет на
`404.html`.

Когда появится сервер:

- Отдавайте настоящий HTTP 404 с телом `404.html`.
- Оставьте `isDeadLink` — сайт всё ещё будет открываться с диска в разработке.
- Сохраните ровно два параметра запроса: `post.html?id=n1` и
  `pictures.html?cat=games&album=al1` (`S.postUrl`, `S.picturesUrl`).
- Один документ отрисовывает любой новостной пост — это сделано намеренно:
  правление может создать пост в консоли, и он станет доступен без добавления
  файла на сервер. Не «исправляйте» это на отдельный файл под каждый пост.

## 19 · Чек-лист безопасности

- [ ] Ни одного пароля, ключа или токена ни в одном файле внутри `js/`
- [ ] Пароли хешированы через argon2id / bcrypt ≥12
- [ ] Сессионная cookie с флагами `HttpOnly` `Secure` `SameSite=Lax`,
      обновляется при входе
- [ ] CSRF-токен на каждом изменяющем состояние запросе
- [ ] Заголовок CSP; единственный внешний источник сейчас — Google Fonts
- [ ] Загрузки: проверка MIME по магическим байтам, лимит размера,
      перекодирование, отдача из пути, который не может исполняться
- [ ] HTML в `copy` санитизируется через белый список
- [ ] Rate limit на вход, форму контактов, форму вступления, загрузку файлов
- [ ] `signups` — это персональные данные: шифрование в состоянии покоя,
      определённый срок хранения, возможность для правления окончательно
      удалить заявку (GDPR — клуб находится в Нидерландах)
- [ ] HTTPS обязателен, HSTS включён

## 21 · Миграция

1. Войдите как админ, откройте консоль, **Danger zone → Copy content as
   JSON**. Это `exportJSON()` в `js/admin.js`, и она отдаёт весь стор целиком
   как ваш сид.
2. Импортируйте его, сохранив каждый `id` и порядок в массиве
   (→ `sort_order`).
3. Извлеките все data URL из `content.images` и из `albums[].photos` в
   настоящие файлы; замените их на URL.
4. Перенастройте `js/data.js` на тот же контент, чтобы офлайн-фолбэк совпадал
   с тем, что отдаёт API.
5. Контент-заглушки правления (`sessions`, `kit`, `pastgames`, бо́льшая часть
   `standings`, `timeline` за 1990-е–2018, `chapters` 02/03/05) —
   **их дело заполнить это в консоли**, не придумывайте это сами и не
   блокируйтесь на этом.

## 22 · Определение «готово»

- Два браузера на двух машинах видят один и тот же контент; правка в одном
  появляется в другом после перезагрузки.
- Неаутентифицированный посетитель не может получить черновик поста, альбом
  участников или список `signups` никаким запросом, включая прямой вызов API.
- Форма контактов отправляет письмо в нужный ящик правления; форма вступления
  создаёт заявку, доступную для рассмотрения, и подтверждает получение заявителю.
- Фото с телефона весом 4 МБ загружается и отображается — без «Storage full».
- В репозитории нет учётных данных; `sign-in.html` не показывает напечатанные пароли.
- Ночной бэкап БД и загрузок, и **восстановление, которое хотя бы раз было
  протестировано**.
- Сайт по-прежнему открывается по `file://` с сохранённым контентом и без
  ошибок в консоли.

## 23 · Предлагаемый порядок работ

| Этап | Содержание |
|---|---|
| **1** | БД + схема на основе `S.schema` · `GET /api/content` · миграция сида |
| **2** | Авторизация: пользователи, сессии, реальный вход · удаление демо-аккаунтов |
| **3** | API записи + проверка прав на сервере · консоль работает с сервером |
| **4** | Загрузки: файлы вне JSON, миниатюры, лимит хранилища исчезает |
| **5** | Формы + e-mail · rate limit · honeypot-поля |
| **6** | 404, кэширование, бэкапы, журнал аудита, сроки хранения по GDPR |

Этапы 1–3 — это, собственно, продукт. 4–6 — то, что позволит ему пережить
передачу дел следующему составу правления.

**Открытые вопросы к правлению, не к вам:** кто выдаёт аккаунты участникам,
как долго хранить `signups`, и может ли участник когда-либо зарегистрироваться
самостоятельно.
